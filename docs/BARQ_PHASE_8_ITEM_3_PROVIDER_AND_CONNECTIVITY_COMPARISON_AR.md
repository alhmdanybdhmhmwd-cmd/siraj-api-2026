# المرحلة 8 — البند الثالث: مقارنة الاتصال والاستضافة والتخزين
التاريخ: 2026-11-21
الفرع: `barq/phase-2-android-ci-2026-11-20`
الحالة: اكتملت المقارنة المكتبية المحدثة؛ اختيار المسار النهائي مشروط باختبارات شبكات يمنية دون VPN. لا تغيير إنتاجي.

## 1. الوضع الحالي المثبت في كود BARQ
- REST: التطبيق يتصل بعنوان Vercel، والـproxy يمرر الطلبات إلى Cloudflare Worker.
- الوسائط: توجد مسارات قديمة في التطبيق تتصل مباشرة بعنوان `workers.dev`؛ هذه نقطة اتصال منفصلة يجب قياسها من اليمن، ولا يكفي نجاح REST عبر Vercel لإثبات نجاح كل الوسائط.
- التخزين الحالي: Tigris S3-compatible خلف Worker؛ التطبيق لا يحتاج مفاتيح Tigris ولا يتصل به مباشرة.
- الرسائل: لا يوجد حتى الآن تنفيذ WebSocket مثبت في Worker/Flutter؛ المسار العامل هو REST polling. لذلك لا نعد WebSocket ميزة جاهزة أو مساراً احتياطياً حالياً.
- رفع الملفات الكبيرة: BARQ يستخدم قطع 1 MiB عبر Vercel proxy ثم Worker؛ هذا يبقى دون حد Vercel الافتراضي البالغ 4.5 MB لكل Function request.

## 2. مقارنة التخزين حسب الأسعار الرسمية المنشورة
| المزود | الحصة المجانية المنشورة | السعر القياسي بعد المجاني | نقل البيانات للخارج | ملاءمته الآن |
|---|---|---|---|---|
| Tigris الحالي | 5 GB، و10,000 طلب Class A، و100,000 طلب Class B شهرياً | 0.02 دولار/GB-month؛ Class A: 0.005 دولار/1000؛ Class B: 0.0005 دولار/1000 | مجاني | الأفضل إبقاؤه حالياً؛ تم بالفعل اختبار الرفع والتنزيل الحقيقيين على Preview بنجاح |
| Cloudflare R2 | 10 GB-month، ومليون Class A، و10 ملايين Class B شهرياً | 0.015 دولار/GB-month؛ Class A: 4.50 دولار/مليون؛ Class B: 0.36 دولار/مليون | مجاني | مرشح اقتصادي قوي لتجربة Preview لاحقاً؛ لكنه لا يحل وحده مشكلة وصول API/DNS من اليمن لأنه لا يغير مسار اتصال الهاتف |
| Backblaze B2 | أول 10 GB مجانية | يبدأ من 6.95 دولار/TB/month حسب السعر المنشور؛ API calls مجانية وفق الخطة المنشورة | مجاني حتى 3 أضعاف متوسط التخزين الشهري، ثم 0.01 دولار/GB عادةً | خيار مستقل عن Cloudflare للتعافي/نسخة احتياطية؛ يحتاج تجربة وصول فعلية وقياس زمن الرفع والتنزيل |

ملاحظة: لا توجد مساحة مجانية غير محدودة. الاحتفاظ الدائم يزيد الاستهلاك مع نمو الملفات، ولذلك يجب وضع تنبيهات للحصة والتكلفة قبل الإطلاق.

## 3. مقارنة طبقة API والاتصال
### Vercel proxy
- مناسب ليكون عنوان API العام الذي يتصل به التطبيق، مع إبقاء Worker كخدمة خلفية.
- حد جسم الطلب الافتراضي لوظائف Vercel هو 4.5 MB. أعلنت Vercel في 20 نوفمبر 2026 عن خيار Public Beta لرفع الحد إلى 20 MiB عبر `VERCEL_SUPPORT_LARGE_REQUEST_BODY=1` مع متطلبات إعداد محددة؛ لم نفعل هذا الخيار، ولا نحتاجه لمسار BARQ الحالي لأن القطع 1 MiB أكثر تحفظاً ويعمل ضمن الحد الافتراضي.
- يجب اختبار DNS وTLS ووقت الاستجابة من شبكات اليمن لكل من عنوان Vercel وعنوان Worker؛ نجاح أحدهما لا يثبت الآخر.

### Cloudflare Workers
- يدعم HTTP streaming، ويدعم WebSocket على مستوى المنصة، لكن دعم المنصة لا يعني أن تطبيق BARQ الحالي نفّذ WebSocket؛ نحتاج بناءه واختباره منفصلاً قبل اعتماده.
- حدود جسم الطلب الواردة إلى Worker على نطاق Cloudflare تصل إلى 100 MB على Free/Pro، لكن حدود الخطة والـCPU والتكلفة تظل واجبة المراجعة قبل توسيع الأحجام أو الحمل.
- إبقاء Worker خلف Vercel proxy يقلل حاجة الهاتف إلى الاتصال المباشر بـ`workers.dev` في المسارات التي يمكن تمريرها عبر proxy. لا نعتبر هذا حلاً مثبتاً حتى نزيل/نراجع جميع المسارات المباشرة ونختبرها على الهاتف.

## 4. القرار الفني المقترح
1. لا ننقل التخزين من Tigris الآن؛ فقد اجتاز Preview اختبار رفع ملف أكبر من 5 MiB، وإعادة التجميع، والتنزيل، والتحقق من SHA-256، وHTTP Range، وصلاحية المستلم.
2. يبقى Vercel عنوان API العام، وCloudflare Worker خلفه، وTigris مخزن الوسائط الحالي؛ لا تغيير على Production أو DNS أو الأسرار.
3. نجهز R2 كخيار Preview بديل للمقارنة الاقتصادية والتقنية فقط إذا أثبتت القياسات سبباً واضحاً للانتقال. لا نربطه بالإنتاج ولا ننسخ إليه بيانات المستخدمين في هذا البند.
4. نحتفظ بـBackblaze B2 كخيار مستقل محتمل للنسخ الاحتياطي/التعافي، لا كبديل فوري.
5. نكمل جرد كل مسارات Android التي تستعمل `workers.dev` مباشرة، ثم نضع خطة توحيدها خلف API proxy في Preview فقط.
6. لا نفعّل WebSocket كمسار الرسائل قبل تنفيذ handler واختبارات reconnect/auth/load؛ REST polling يبقى المسار الموثوق حالياً.

## 5. مصفوفة اختبار اليمن المطلوبة قبل القرار النهائي
هذه الاختبارات لم تُنفذ بعد من شبكات يمنية فعلية، ولا يمكن لاستضافة CI خارج اليمن أن تحل محلها:

| الاختبار | Yemen Net | Yemen Mobile | شبكة يمنية ثانية/مختلفة | خارج اليمن |
|---|---|---|---|---|
| DNS resolve لعناوين Vercel وWorker | معلق | معلق | معلق | يُقاس |
| TLS handshake وHTTP health | معلق | معلق | معلق | يُقاس |
| تسجيل الدخول وREST | معلق | معلق | معلق | يُقاس |
| رفع/تنزيل صغير وكبير عبر المسار العام | معلق | معلق | معلق | يُقاس |
| SPARK والذكريات الخاصة | معلق | معلق | معلق | يُقاس |
| قياس latency وtimeouts ونسب الفشل | معلق | معلق | معلق | يُقاس |

يجب تسجيل وقت الاختبار، نوع الشبكة، نتيجة DNS/TLS/HTTP، وزمن الاستجابة، دون تسجيل أرقام هواتف أو رموز دخول أو محتوى الرسائل.

## 6. بوابة الأمان
- لا تعديل DNS أو نطاقات الإنتاج أو إعدادات Vercel/Worker الإنتاجية.
- لا نقل bucket أو حذف/نسخ ملفات إنتاج.
- لا تبديل مزود التخزين أو إضافة اعتماد على R2/B2 إلى تطبيق المستخدم قبل اختبار اليمن دون VPN وموافقة المستخدم الصريحة.
- لا نعلن حل مشكلة VPN قبل اجتياز اختبارات اليمن الفعلية على شبكتين على الأقل.

## الخلاصة
المقارنة لا تدعم نقل التخزين الآن. Tigris يعمل على Preview بعد نجاح اختبار الوسائط، وR2 أوفر على الورق لكنه لا يعالج نقطة DNS/الاتصال بالـAPI، وB2 يوفر استقلالاً إضافياً مع شروط egress مختلفة. القرار الآمن هو الإبقاء على البنية الحالية مؤقتاً، وإجراء اختبار الوصول من اليمن قبل اعتماد أي تغيير.
