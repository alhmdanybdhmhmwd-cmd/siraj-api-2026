# تشغيل API برق المستقل على Node.js

## الحالة

هذا مدخل تشغيل مستقل عن Cloudflare، ويستعمل نفس Worker handler ونفس مسارات BARQ، مع تزويده بموائم libSQL بدلاً من D1. لا يقوم هذا المدخل بنشر التطبيق أو نقل قاعدة البيانات تلقائياً.

## المتطلبات

- Node.js 20 أو أحدث.
- عنوان قاعدة libSQL/Turso في `LIBSQL_URL` ورمزها عند الحاجة في `LIBSQL_AUTH_TOKEN`.
- سر JWT مستقل وآمن في `JWT_SECRET`.
- بيانات اعتماد S3-compatible/Tigris اختيارية حتى تفعيل مسارات الوسائط.
- بيانات حساب Firebase اختيارية حتى إرسال إشعارات FCM.

انسخ `.env.example` إلى ملف إعدادات خاص ببيئة التشغيل، ولا ترفع الملف الذي يحتوي أسراراً إلى Git.

## التشغيل

```sh
npm install
npm start
```

يبدأ الخادم على `0.0.0.0:8787` افتراضياً. يمكن تغيير العنوان والمنفذ عبر `HOST` و`PORT`.

- `GET /health/live`: فحص أن HTTP API يعمل.
- `GET /health/ready`: فحص جاهزية قاعدة البيانات والسر المطلوب.
- يبدأ تنظيف البيانات المجدول كل 15 دقيقة، مع منع تداخل عمليتي تنظيف.
- أمر `npm run start:proxy` يبقي proxy القديم متاحاً لأغراض التوافق، ولا يمثل محرك API المستقل.

## ما يمر عبر المحرك المستقل

- نفس Worker fetch handler ونفس REST routes والصلاحيات.
- libSQL عبر `createLibsqlDatabaseProvider` مع واجهة D1 المتوافقة.
- تخزين S3/Tigris عبر موائم التخزين الحالي.
- FCM عبر خدمة الإشعارات المستخرجة.
- جدولة التنظيف كل 15 دقيقة، مع انتظار المهام الجارية وتصريف مهام الطلبات قبل إغلاق قاعدة البيانات.

## الحدود الحالية

- لا تُطبق migrations تلقائياً عند بدء التشغيل. يجب تجهيز مخطط قاعدة Preview مسبقاً ومراجعته قبل توجيه أي طلبات إليها.
- لا يوجد نسخ أو نقل لبيانات D1 الإنتاجية.
- Workers AI غير متاح تلقائياً في Node؛ يمكن حقن مزود AI متوافق برمجياً، وإلا تبقى قدراته غير مهيأة في هذا المضيف.
- هذا البناء لا يثبت بعد اتصال Turso/S3/FCM الخارجي من شبكة اليمن، ولا يثبت حل مشكلة VPN.
- لا تغييرات DNS أو Cloudflare bindings أو تخزين الإنتاج ضمن هذه الخطوة.

## اختبارات التحقق

تتضمن `test/node_server.test.mjs` اختبارات عقد HTTP، وطرق HEAD/OPTIONS، وتمرير Authorization وRange والبايتات الثنائية، وفشل readiness، واختبار تشغيل Worker الحقيقي عبر HTTP مع قاعدة libSQL محلية مؤقتة.
