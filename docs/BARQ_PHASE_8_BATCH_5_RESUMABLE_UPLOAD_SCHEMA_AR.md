# المرحلة 8 — الدفعة الخامسة: مخطط جلسات الرفع القابل للاستئناف

## ما تم
- إضافة الترحيل `migrations/0010_resumable_media_uploads.sql`.
- إنشاء `media_upload_sessions` لحفظ المالك والمستلم أو المجموعة ومفتاح الكائن ومعرّف multipart لدى التخزين وبيانات الملف وحالة الجلسة وموعد انتهاء الجلسة.
- فرض حدود الحجم 1–60 MiB، وحجم الجزء 5 MiB، وعدد الأجزاء 1–12.
- فرض مفتاح idempotency فريد لكل مالك لمنع إنشاء جلسات مكررة عند إعادة الطلب.
- إنشاء `media_upload_parts` لحفظ رقم الجزء وETag والحجم مع مفتاح مركب يمنع تسجيل الجزء نفسه مرتين.
- إضافة فهارس للبحث عن الجلسات المنتهية وجلسات المالك.
- ربط الجلسات بالمستخدمين، وربط الأجزاء بالجلسة مع الحذف المتسلسل لسجلات الأجزاء عند حذف سجل الجلسة.

## ضمانات وحدود مهمة
- انتهاء `expires_at` هنا يخص جلسة الرفع غير المكتملة فقط، ولا يحدد مدة بقاء الملف النهائي.
- لا توجد في هذا الترحيل أي أوامر لحذف كائنات Tigris أو تغيير سياسة الاحتفاظ بمرفقات المحادثات أو SPARK.
- لا توجد بعد نقاط API لبدء الرفع أو إرسال الأجزاء أو الإكمال أو الإلغاء؛ هذه هي الخطوة البرمجية التالية.
- لم يتم ربط Flutter بعد.
- لم يتم الاتصال بتخزين Tigris فعلياً أو اختبار استئناف حي بعد انقطاع.
- لم يتم نشر Preview أو تغيير أي بيئة إنتاج أو DNS أو بيانات.

## المتبقي في الدفعة
1. بناء API آمن لبدء الجلسة مع تحقق من ملكية المستلم أو عضوية المجموعة.
2. بناء API لرفع كل جزء والتحقق من الحجم وETag وidempotency.
3. بناء API للإكمال والتحقق من اكتمال كل الأجزاء بالترتيب، ثم إنشاء سجل المرفق ورسالة المحادثة بشكل متسق.
4. بناء API للإلغاء وتنظيف الجلسات المؤقتة المنتهية دون لمس الملفات النهائية.
5. اختبارات D1 معزولة ومحاكاة أخطاء التخزين والانقطاع والتكرار.
