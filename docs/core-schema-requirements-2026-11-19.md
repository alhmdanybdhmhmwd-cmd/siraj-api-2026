# Core D1 schema contract and isolated Preview fixture

Date: 2026-11-19

## Purpose and safety

This document records the minimum schema contract implied by the current Worker source. No authoritative production D1 export or base migration exists in the repository. A separate **Preview-only fixture migration** (`migrations/0003_preview_core_schema.sql`) has now been added and applied to the dedicated test database. It exists only to exercise the Worker contract and is **not an export or replica of production D1**. Never apply it through `wrangler.toml` or to production.

## `users`

### Columns directly referenced
- `id`: primary identity; referenced by support-table foreign keys and used in account lookups.
- `username`: registration/login identity; lowercased by registration and queried by exact match and LIKE.
- `display_name`: required at registration; returned in profile, search, and contacts.
- `password_hash`, `password_salt`: password verification and password reset.
- `phone`: nullable in registration/profile flows; searched through local/international phone normalization.

### Behavioral constraints established by code
- Registration rejects an existing username through the existing insert path and checks phone equivalence using normalized phone variants.
- Profile updates check equivalent phone variants before changing the value.
- Do not assume a plain UNIQUE(phone) index is sufficient: local and international forms may represent the same number, while the Worker performs normalization-aware conflict checks.
- Authentication supports username or normalized phone lookup.

### Still unknown
Exact SQL types, username collation/unique index, ID generation policy at the database layer, phone nullability in the deployed schema, and all FK/index definitions.

## `friendships`

### Columns directly referenced
- `user_id`
- `friend_id`

### Behavioral constraints established by code
- Adding a contact inserts both directions using `INSERT OR IGNORE`.
- Reads and authorization checks query a directed pair (`user_id`, `friend_id`).
- Status visibility, private messaging, and attachment authorization depend on these directed relationships.

### Still unknown
Whether the deployed schema uses a composite primary key or unique constraint, FK actions, timestamps, and supporting indexes. A uniqueness rule on the directed pair is strongly suggested by `INSERT OR IGNORE`, but must be verified from the actual database before being prescribed.

## `messages`

### Columns directly referenced
- `id`
- `sender_id`
- `receiver_id`
- `body`
- `created_at`
- `read_at`

### Operations established by code
- Private text messages are inserted with `id`, `sender_id`, `receiver_id`, and `body`.
- Attachment messages are also inserted into this table using the same four-column insert shape; the body contains the attachment reference/metadata representation generated by the Worker.
- Read receipts update `read_at` for messages matching sender and receiver direction.
- Conversation history selects `id, sender_id, receiver_id, body, created_at, read_at` for either direction between two users.

### Still unknown
Exact types, defaults for `created_at`, whether `read_at` is nullable, message ordering/indexes, retention rules, and any other columns present in the deployed schema. Do not assume that the six observed columns are the complete table definition.

## Preview-only fixture migration and verification

`migrations/0003_preview_core_schema.sql` creates the minimum `users`, `friendships`, and `messages` tables required by the current Worker SQL contract. Its types, `username` case-insensitive uniqueness, directed friendship-pair uniqueness, foreign keys, and query indexes are explicit test-fixture decisions. In particular, the fixture deliberately does **not** put a simple UNIQUE constraint on `phone`; equivalent local/international forms are checked by Worker normalization logic.

The migration was applied successfully to the dedicated isolated D1 database `barq-phase2-test-2026-11-20` (ID `5bfada32-4f9b-4edb-85dd-3b3b30ab73b0`) by workflow run `44804926838`. The workflow inspected `sqlite_master`, columns, and indexes without reading account rows. Backend SQLite migration tests now execute all three versioned migrations and verify registration-compatible user columns, duplicate username rejection, non-unique phone storage, duplicate directed-contact prevention, message insertion/read receipts, and core foreign keys.

This enables functional testing against a coherent Preview fixture, but it does **not** prove that production D1 uses identical types, indexes, or constraints. If production parity is required later, obtain a read-only schema export from a verified backup or an authorized isolated clone and compare it separately. Never inspect or mutate production as part of this phase.
