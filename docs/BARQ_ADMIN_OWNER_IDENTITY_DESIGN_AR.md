# تصميم هوية المالك وجلسات BARQ Admin

**النطاق:** المرحلة 1 من BARQ Admin فقط  
**الحالة:** اعتمد المالك Google OIDC + PKCE؛ نُفذ أساس الخادم ومخطط الجلسات، وربط تطبيق الهاتف والاختبارات قيد الاستكمال. لم يُنشر أو يُختبر على جهاز بعد  
**الفرع:** `barq-admin-foundation-2026-11-23`

## الهدف

استبدال إدخال Bearer token يدويًا في تطبيق Flutter بتسجيل دخول موثوق للمالك، مع جلسات أجهزة يمكن إبطالها وتجديدها، دون خلط هوية BARQ Admin بهوية مستخدمي تطبيق BARQ.

## الوضع الحالي المؤكد

- يتحقق Admin Worker من JWT موقّع بـ HS256، ويثبت `iss=barq-admin-auth` و`aud=barq-admin` و`sub` مقابل `BARQ_ADMIN_OWNER_SUBJECT`.
- لا يوجد في المشروع حاليًا token issuer أو تدفق تسجيل دخول مالك.
- تطبيق Flutter يطلب عنوان API ورمز Bearer يدويًا ويحفظ الرمز في secure storage.
- لا يوجد سجل أجهزة/جلسات على الخادم، ولا refresh-token rotation أو device revocation.
- لا توجد بيئة Admin Preview موثقة ومختبرة لتشغيل تدفق الهوية كاملًا.

## القرار المعتمد\n\nاعتمد المالك Google OpenID Connect باستخدام Authorization Code + PKCE عبر AppAuth. يُسمح لحساب Google واحد فقط من خلال `BARQ_ADMIN_OWNER_EMAIL` مع التحقق من `email_verified=true`، ويمكن تثبيت قيمة `sub` عبر `BARQ_ADMIN_OWNER_SUBJECT` بعد أول تهيئة. لا تُطلب صلاحيات Gmail أو Drive.\n\n## البنية المستهدفة

1. **Google OIDC**: يستخدم تطبيق الهاتف Authorization Code + PKCE عبر AppAuth، مع `openid`, `email`, `profile` فقط. لا تُخزن كلمة مرور المالك في BARQ Admin.
2. **Admin identity exchange**: يتحقق خادم BARQ Admin من توقيع ورمز هوية المزود، ثم يطابق issuer وaudience وsubject مع إعدادات المالك المسموح به. لا يقبل التطبيق اختيار subject أو role.
3. **جلسة Admin مستقلة**: يصدر الخادم access token قصير العمر، ويربطه بسجل جلسة وجهاز على قاعدة Admin D1 فقط.
4. **Refresh rotation**: يصدر refresh token عشوائي عالي العشوائية، ولا يخزن الخادم قيمته الخام؛ يخزن hash فقط. كل استخدام ناجح يستبدل الرمز ذريًا، وإعادة استخدام رمز قديم تبطل سلسلة الجلسة وتُسجل حدثًا أمنيًا.
5. **إدارة الأجهزة**: قائمة جلسات المالك، إبطال جهاز محدد، وإبطال جميع الجلسات. يجب أن يُرفض access token فور إبطال جلسته، حتى لو لم تنته مدة JWT.
6. **فصل المنتجات**: لا تُقبل جلسات BARQ Admin في API المستخدمين، ولا تُقبل جلسات مستخدمي BARQ في Admin API. لا اتصال مباشر من تطبيق الإدارة إلى قاعدة بيانات BARQ.

## عقود API المقترحة

- `POST /v1/auth/exchange`: تبادل إثبات الهوية الموثوق عن طريق الخادم وإنشاء جلسة جهاز.
- `POST /v1/auth/refresh`: تدوير refresh token وإصدار access token جديد.
- `POST /v1/auth/logout`: إبطال الجلسة الحالية.
- `GET /v1/devices`: عرض جلسات وأجهزة المالك النشطة.
- `DELETE /v1/devices/:id`: إبطال جلسة جهاز محدد.
- `POST /v1/devices/revoke-all`: إبطال جميع الجلسات، مع استثناء الجلسة الحالية فقط إذا كان ذلك مطلوبًا ومؤكدًا في UX.

هذه عقود تصميم وليست مسارات عاملة حاليًا. يجب حماية كل مسار ومراجعته قبل إتاحته.

## مخطط البيانات المطلوب

- `admin_owner_devices`: معرف الجهاز، المالك، اسم/نوع الجهاز، وقت الإنشاء وآخر نشاط، حالة الإبطال.
- `admin_owner_sessions`: معرف الجلسة، الجهاز، hash لرمز التجديد الحالي، تاريخ الانتهاء، وقت الإبطال، ومؤشر إصدار/تدوير.
- فهارس على المالك والجهاز وحالة الجلسة وتاريخ الانتهاء.
- لا تُخزن refresh tokens الخام أو كلمات المرور أو رموز مزود الهوية طويلة العمر في قاعدة البيانات أو السجلات.
- سجلات الإبطال وتدوير الرموز تُكتب في audit events غير القابلة للتعديل.

## قواعد أمنية غير قابلة للتفاوض

- لا يُضمّن أي signing secret أو client secret داخل APK.
- لا يُقبل HS256 token لمجرد صحة التوقيع؛ يجب أن تكون له جلسة خادم نشطة وغير ملغاة.
- access token قصير العمر؛ refresh token أحادي الاستخدام مع تدوير ذري وحماية من replay.
- تحديد معدل محاولات الدخول والتجديد، ورسائل خطأ لا تكشف وجود الحساب أو تفاصيل الأسرار.
- حماية CSRF عند استخدام cookies؛ التطبيق الأصلي يستخدم Authorization header ولا يعتمد على جلسة متصفح.
- التحقق من `iss`, `aud`, `exp`, `nbf`, `sub`, `jti` وخوارزمية التوقيع المسموحة، مع تدوير مفاتيح موثق.
- سجّل أحداث الدخول والرفض والتجديد والإبطال دون تسجيل أي رمز أو سر.
- لا تعتمد على device ID يرسله العميل كعامل مصادقة؛ هو وصف للجهاز فقط.
- لا تفعّل حسابات موظفين أو أدوارًا مفوضة في هذه المرحلة؛ النطاق مالك واحد محدد.

## اختبارات القبول المطلوبة

1. دخول مالك صحيح وإنشاء جلسة وجهاز.
2. رفض هوية مزورة، issuer أو audience خاطئ، subject غير المسموح، توقيع غير صالح، رمز منتهي أو قبل وقت الصلاحية.
3. رفض access token عند غياب سجل الجلسة أو إبطالها.
4. نجاح refresh مرة واحدة، ورفض إعادة استخدام refresh token القديم مع إبطال سلسلة الجلسة وفق السياسة.
5. إبطال جهاز واحد يمنع استخدام access وrefresh الخاصين به.
6. إبطال كل الأجهزة يمنع كل الجلسات السابقة.
7. انتهاء الجلسة والخروج وإعادة الدخول يعملان دون فقد بيانات workspace.
8. لا تظهر الأسرار أو الرموز في السجلات أو استجابات API.
9. اختبارات التزامن: طلبا refresh متزامنان لا ينتجان جلستين صالحَتين من الرمز نفسه.
10. اختبار Flutter على Android: login، refresh بعد انتهاء access، logout، عرض الأجهزة وإبطال جهاز.

## قرار مطلوب قبل التنفيذ

يجب اختيار مزود هوية يدعم OIDC وPKCE وتحديد حساب المالك المسموح به، ثم إعداد بياناته السرية في بيئة خادم Preview فقط. لا أختار مزودًا ولا أطلب أو أخزن كلمة مرور أو سرًا داخل المحادثة. بعد اعتماد المزود، ينفذ التكامل على فرع الإدارة ويُختبر في موارد Preview معزولة.
