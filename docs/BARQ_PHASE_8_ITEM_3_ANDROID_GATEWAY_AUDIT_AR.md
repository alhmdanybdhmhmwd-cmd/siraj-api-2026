# المرحلة 8 — تدقيق مسارات Android وبوابة API (2026-11-21)

الحالة: اكتمل تدقيق ملفات Android المتصلة بالشبكة وإصلاح تمرير بيانات SPARK عبر البوابة. لا يثبت هذا التقرير نجاح الاتصال من اليمن دون VPN.

## 1. النطاق الذي تمت مراجعته
- `android/lib/main.dart`: عناوين API والوسائط وWebSocket، رفع الصور والملفات، رفع SPARK، الردود الصوتية، تنزيل الوسائط، تشغيل الفيديو، وتحويل الصوت إلى نص.
- Android manifests وملفات Kotlin وFlutter tests.
- `api/[...path].js`: بوابة Vercel إلى Worker، رؤوس الطلبات، CORS، حدود الأحجام، Range، وبث استجابات الوسائط.
- اختبارات `test/proxy.test.mjs` و`test/vercel_proxy_preview.test.mjs` واختبارات عقد Android.

## 2. نتائج جرد Android
- `BARQ_API_BASE` افتراضياً: `https://siraj-api-2026.vercel.app`.
- `BARQ_MEDIA_BASE` افتراضياً: نفس عنوان API العام.
- `BARQ_REALTIME_URL` افتراضياً فارغ؛ لا يعتمد التطبيق افتراضياً على WebSocket مباشر إلى `workers.dev`.
- عمليات REST والوسائط والذكريات وSPARK تمر افتراضياً عبر عنوان API العام.
- لم يظهر عنوان Tigris أو `workers.dev` ضمن ملفات Android التشغيلية التي تمت مراجعتها، عدا الإشارات التوثيقية/التعليقات التي تشرح سبب تجنب الاتصال المباشر.
- يوجد مسار احتياطي قابل للتهيئة عبر `BARQ_MEDIA_BASE`، لكنه ليس مزوداً مستقلاً بعد؛ القيمة الافتراضية واحدة مع API.

## 3. خلل عُثر عليه وأُصلح
بوابة Vercel كانت تمرر بعض الرؤوس فقط، بينما Flutter يرسل بيانات لازمة لبعض عمليات الوسائط:
- `X-Status-Caption`
- `X-Status-Id`
- `X-Audio-Duration-Ms`
- `X-Idempotency-Key`

أضيف تمرير هذه الرؤوس إلى Worker، وأضيفت تغطية اختبارية لرفع وسائط SPARK والرد الصوتي، مع تحديث CORS للسماح بها. هذا يمنع فقد بيانات وصف SPARK ومعرّف الحالة ومدة التسجيل أثناء المرور عبر بوابة API.

## 4. تحسين محاولات تنزيل الوسائط
كان التطبيق يحاول أحياناً عنوان الوسائط ثم يعيد المحاولة على عنوان API، رغم أن العنوانين متطابقان افتراضياً. أضيف helper يجرب كل عنوان مميز مرة واحدة فقط:
- يستجيب مباشرة لأخطاء العميل مثل 401/403/404 ولا يعيد الطلب على عنوان آخر.
- يجرب العنوان البديل فقط عند خطأ شبكة أو خطأ خادم 5xx.
- يمنع تكرار نفس الطلب إلى نفس hostname عندما يكون الإعداد الافتراضي موحداً.

- لم يُنشأ APK للمستخدم ولم يحدث نشر إنتاجي.

## 6. حدود ما ثبت
- نجاح CI يثبت صحة الاختبارات البرمجية فقط، ولا يثبت أن مزود Vercel أو Worker متاح من كل شبكات اليمن.
- لا يوجد حتى الآن قياس DNS/TLS/HTTP من يمن نت أو يمن موبايل أو شبكة يمنية ثانية دون VPN.
- عنوان Vercel العام يمرر الطلبات من جهة الخادم إلى Worker الحالي؛ لم يُنشأ بعد مزود API مستقل ثانٍ أو failover بين مزودين مستقلين.
- لا نعتبر إخفاء hostname الخاص بـWorker خلف Vercel علاجاً نهائياً إذا كانت المشكلة من حجب أو توجيه على مستوى الشبكة أو من مزود الخدمة نفسه.

## 7. الخطوات المتبقية
1. اكتمل Android quality gate بنجاح؛ تبقى الاختبارات الحية عبر Preview والشبكات اليمنية.
2. اختبار health/live وhealth/ready على Preview عبر بوابة Vercel نفسها، لا الاكتفاء باستدعاء Worker مباشرة.
3. قياس DNS وTLS وREST ورفع/تنزيل ملفات صغيرة وكبيرة من شبكات يمنية فعلية دون VPN، وتسجيل زمن الاستجابة وأخطاء الاتصال دون جمع بيانات شخصية.
4. تصميم واختبار بديل API مستقل إذا أثبتت القياسات أن المسار الحالي لا يعمل على الشبكات اليمنية.
5. لا تعديل إنتاج أو DNS أو bucket أو أسرار إنتاج ولا تفعيل أي تغيير قبل إثبات الوصول من اليمن وموافقة المستخدم الصريحة.

## الخلاصة
توحيد مسار Android الافتراضي وإصلاح تمرير رؤوس SPARK وتحسين إعادة المحاولة اكتمل برمجياً واختبارات Backend نجحت. البند الثالث لا يُغلق نهائياً بعد؛ اختبار Android الجاري والقياس الفعلي من اليمن دون VPN وبوابة failover مستقلة ما زالت مطلوبة.

- يلزم بعد عودة حصة النشر أو حل صلاحية Preview: نشر commit الحالي إلى Preview فقط، ثم السماح باختبار health عبر رابط Preview محمي بطريقة آمنة (من دون كشف أي token في المحادثة)، وإعادة قياس DNS/TLS/HTTP.

## 10. إصلاح توافق CORS بين البوابة وWorker (2026-11-21)
- كشف التدقيق أن Vercel gateway يسمح بـPUT لكنه لم يعلن PATCH في CORS، كما لم يعلن Range ضمن الرؤوس المسموحة. Worker بدوره لم يعلن PUT أو X-Idempotency-Key أو Range، ولم يكشف رؤوس استجابة HTTP Range للعميل.
- تمت مواءمة الجهتين: PUT وPATCH، والرؤوس Range وX-Idempotency-Key، وكشف Content-Range وAccept-Ranges وETag وX-Request-Id.
- أضيفت اختبارات عقد Worker واختبار preflight فعلي لبوابة Vercel يغطي تعديل الرسائل والرفع المجزأ وتنزيل أجزاء الملف.
- Backend CI على commit e39ab3e3f34c06c7df9877f33db7f62d0446fed0 نجح: 216/216 اختباراً، دون فشل، run [44946754896](https://github.com/alhmdanybdhmhmwd-cmd/siraj-api-2026/actions/runs/44946754896). تكرار CI على commit نفسه run [44946761090](https://github.com/alhmdanybdhmhmwd-cmd/siraj-api-2026/actions/runs/44946761090) نجح أيضاً.
- هذا إصلاح لتوافق CORS وليس دليلاً على تجاوز حجب الشبكات أو حل VPN. لم يحدث نشر جديد أو تغيير DNS أو إعداد إنتاج.

## 11. تجهيز خيار API failover اختياري وآمن (2026-11-21)
- أضيف إلى Vercel gateway خيار خادم احتياطي server-side عبر متغير اختياري BARQ_API_FALLBACK_UPSTREAM. لا يوجد عنوان احتياطي مضبوط حالياً، لذلك يبقى الخيار غير مفعّل ولا يغيّر حركة الإنتاج.
- لا يقبل الإعداد الاحتياطي إلا HTTPS origin صالحاً ومختلفاً عن الأساسي؛ الروابط ذات المسارات أو العناوين غير الآمنة تُهمل. بيئة Preview تبقى مثبتة على Worker الاختبار المعزول وتتجاهل أي override أو fallback.
- عند وجود عنوان احتياطي، يسمح التحويل إليه بعد فشل الشبكة أو استجابات 502/503/504 فقط. لا يعاد إرسال POST أو PATCH غير القابل للتكرار؛ POST لا يعاد إلا مع X-Idempotency-Key. GET/HEAD/PUT/DELETE/OPTIONS قابلة لإعادة المحاولة وفق دلالاتها.
- أضيفت اختبارات تغطي 503، وفشل الشبكة/DNS، وPOST مع idempotency key، ومنع تكرار POST العادي، ورفض HTTP أو fallback غير صالح، وعزل Preview.
- Backend CI على commit 4d906fb7da2d1602176dbe5ebf7efcf197c93502 نجح: 222/222 اختباراً دون فشل، run [44947186202](https://github.com/alhmdanybdhmhmwd-cmd/siraj-api-2026/actions/runs/44947186202). كما نجح فحص Worker المحلي وhealth probes على run [44946683888](https://github.com/alhmdanybdhmhmwd-cmd/siraj-api-2026/actions/runs/44946683888).
- لم يُنشأ أو يُفعّل خادم احتياطي فعلي بعد؛ لا يوجد حتى الآن عنوان مستقل تم التحقق من DNS/TLS/الوصول إليه من اليمن. لا يعتبر هذا حلاً مثبتاً للـVPN، ولا تم نشر أي تعديل على الإنتاج أو تغيير DNS أو التخزين.
- الخطوة التالية: اختيار مزود/نطاق مستقل، نشر Worker احتياطي معزول بعد موافقة المستخدم، ثم اختباره من اليمن دون VPN قبل وضع أي إعداد إنتاجي.
