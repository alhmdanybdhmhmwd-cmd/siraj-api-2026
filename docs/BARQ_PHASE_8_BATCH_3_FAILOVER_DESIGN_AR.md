# المرحلة 8 — الدفعة الثالثة: تصميم مسار اتصال احتياطي دون تغيير الإنتاج
التاريخ: 2026-11-21
الحالة: تصميم موثق فقط — لا نشر ولا تعديل على التطبيق أو الإنتاج.

## شرط المستخدم الحاكم
لا يُسمح بتفعيل أي تغيير في التطبيق أو الخوادم أو التخزين أو DNS قبل إثبات أن BARQ يعمل دون VPN. نجاح CI أو نجاح اختبار من خارج اليمن لا يُعد إثباتاً. لا يتم الانتقال إلى تفعيل الحل إلا بعد اختبار شبكي فعلي من اليمن دون VPN، ثم موافقة المستخدم.

## ما كشفته مراجعة المسارات
- REST في التطبيق يذهب إلى Vercel افتراضياً.
- Vercel proxy يمرر الطلب إلى Worker.
- رفع الملفات الصغيرة (حتى 4 MiB) يمر عبر Vercel، والكبيرة تتصل مباشرةً بعنوان workers.dev.
- صور SPARK والذكريات الخاصة وبعض ردود الصوت تتصل مباشرةً بـWorker.
- WebSocket غير مثبت التشغيل: لا يوجد handler مطابق في Worker، ولا يوجد استدعاء start في Flutter؛ المحادثات تستخدم REST polling كل 5 ثوانٍ.
- إذن تغيير اسم نطاق Worker وحده لن يكفي إذا بقيت روابط الوسائط المباشرة داخل التطبيق.

## التصميم المقترح (Preview أولاً)
### A. عنوان اتصال واحد من التطبيق
- اعتماد عنوان API عام واحد فقط في إعداد التطبيق.
- إبقاء عنوان Worker داخلياً خلف proxy server-side؛ لا يطلب التطبيق مباشرةً من workers.dev.
- تمرير REST، الصور، وسائط SPARK، الذكريات الخاصة، وردود الصوت عبر المسار الوسيط نفسه.
- لا نستخدم WebSocket كشرط لتشغيل الرسائل؛ يبقى REST هو مسار الرسائل الموثوق حتى يُبنى WebSocket ويُختبر بشكل مستقل.

### B. الملفات الأكبر من حد Vercel
- لا نمرر ملفاً كبيراً واحداً إلى Vercel؛ حد طلبات Vercel Function يقارب 4.5 MB.
- تصميم رفع مجزأ قابل للاستئناف: يجزّئ التطبيق الملف محلياً إلى أجزاء أصغر من الحد (مثلاً 2 MiB)، ويرسل كل جزء كطلب مستقل إلى عنوان API العام.
- Vercel يمرر كل جزء إلى Worker، وWorker يدير جلسة رفع ذات معرف عشوائي ومصادقة، ثم يكتب الأجزاء/يكمل multipart upload إلى Tigris.
- لا يتم إعلان نجاح المرفق في المحادثة إلا بعد اكتمال التجميع والتحقق من الحجم والبصمة وتسجيل metadata في D1.
- عند انقطاع الشبكة يعاد إرسال الجزء الفاشل فقط، مع idempotency key لمنع التكرار.
- التنزيل الكبير يحتاج دعماً موازياً للـRange أو تنزيل مجزأ مع تحقق من كل جزء؛ لا يُعتمد buffering كامل في Vercel.

### C. التشخيص والاختبار
- إنشاء health/readiness probe للـPreview فقط، لا يعرض أسراراً، ويقيس اتصال Vercel بالـWorker وD1 وTigris بقراءة غير مغيرة.
- إضافة correlation ID وقياسات زمنية وفئات الأخطاء (DNS/TLS/timeout/5xx/4xx) دون تسجيل الرموز أو محتوى الرسائل.
- الاختبارات من اليمن دون VPN يجب أن تغطي: تسجيل الدخول/REST، المحادثات، رفع ملف صغير، رفع ملف أكبر من 4 MiB، تنزيله، صور SPARK، صور الذكريات، ثم إعادة الاختبار عبر مزود إنترنت آخر.
- نكرر الاختبار مع VPN مغلق تماماً، ونسجل اسم الشبكة والوقت ونوع النتيجة؛ لا نحتاج رقم الهاتف أو بيانات حساب حقيقية في التقرير.

## ضوابط الأمان والبيانات
- لا تغيير DNS أو الدومين الحالي أو Worker production أو Vercel production.
- لا نقل bucket أو نسخ/حذف ملفات فعلية.
- لا تعطيل Cron أو تغيير سياسة 72 ساعة في هذه الدفعة.
- لا تغيير مسارات التطبيق الحالي قبل اجتياز Preview والاختبار اليمني.
- جلسات الرفع المؤقتة لها انتهاء قصير وتنظيف منفصل، ولا يجوز أن تنطبق مدة الجلسة على المرفق النهائي.
- التحقق من المالك/المستلم/المجموعة على كل جزء، وعدم السماح بتغيير بيانات الجزء أو استبدال ملف جلسة أخرى.
- لا تخزين لرموز المصادقة أو محتوى الرسائل في السجلات.

## بوابة الإثبات قبل أي تفعيل
يعتبر حل VPN مثبتاً فقط إذا:
1. نجح التطبيق في الوظائف الأساسية دون VPN من شبكة يمنية فعلية.
2. نجحت الوسائط الصغيرة والكبيرة وSPARK والذكريات دون VPN.
3. تكرر النجاح على شبكة يمنية ثانية أو تم توثيق حدود الشبكة الأولى بدقة.
4. لا توجد أخطاء مصادقة أو فقد ملفات أو تكرار رسائل.
5. راجع المستخدم النتائج وأعطى موافقة صريحة على نقل التغيير للنسخة التالية.

## ما يلي هذه الدفعة
تنفيذ نموذج الرفع المجزأ ومسارات proxy في بيئة Preview مع اختبارات آلية معزولة فقط. لن تُجرى أي تغييرات في الإنتاج أو تُفعّل في نسخة المستخدم قبل اجتياز بوابة الإثبات أعلاه وموافقة المستخدم.
