# برق — تسليم المرحلة 8 قبل الانتقال إلى المرحلة 9

تاريخ المراجعة: 2026-11-21
الفرع: `barq/phase-2-android-ci-2026-11-20`

## قرار نطاق العمل بعد توجيه المستخدم

- تستمر المعالجة البرمجية للمرحلة 8 الآن، ويُجهّز تسليم واضح للمرحلة 9 دون إسقاط أي ميزة أو اتفاق سابق.
- تُرحّل اختبارات الهواتف والشبكات اليمنية الحقيقية، واختبارات التكامل/التحمل النهائية، إلى بوابة الاختبارات في المرحلة 12 ثم تدقيق المرحلة 13 قبل النسخة التجريبية.
- لا يُعد هذا الترحيل تنازلاً عن معيار VPN: لا يُترك عيب اتصال معروف يمكن إصلاحه برمجياً، ولا يُعلن أن الاتصال دون VPN مضمون قبل اختبار فعلي من اليمن.
- لا نشر إنتاج، ولا تغيير DNS، ولا تغيير تخزين إنتاج، ولا توجيه التطبيق إلى مزود بديل قبل إثبات الوصول من اليمن دون VPN وموافقة المستخدم.

## ما تحقق من فحص المستودع

1. آخر تحديث لدراسة مزود API مستقل موجود في `docs/BARQ_PHASE_8_INDEPENDENT_API_PROVIDER_STUDY_AR.md`.
2. Backend CI على commit `910b8616706cf752de77beb5b32ba28e190f0f2e` نجح في التشغيلين:
   - [44947930676](https://github.com/alhmdanybdhmhmwd-cmd/siraj-api-2026/actions/runs/44947930676)
   - [44947935513](https://github.com/alhmdanybdhmhmwd-cmd/siraj-api-2026/actions/runs/44947935513)
3. بوابة Vercel الحالية تدعم fallback اختياريًا عبر `BARQ_API_FALLBACK_UPSTREAM`، لكنه غير مضبوط؛ لذلك لا يوجد failover مستقل فعّال حالياً.
4. بوابة Preview مثبتة على Worker الاختبار المعزول ولا تسمح بتحويل Preview إلى Production أو إلى fallback override.
5. إعادة المحاولة محدودة بالأخطاء الشبكية و502/503/504، وتحمي عمليات POST/PATCH غير القابلة للتكرار؛ لا تعيد كتابات POST/PATCH إلا مع `X-Idempotency-Key`.
6. Android يستخدم عنوان API موحداً افتراضياً لـAPI والوسائط عبر Vercel، بينما WebSocket معطل افتراضياً. هذا يقلل الاعتماد المباشر على `workers.dev` لكنه لا يعالج وحده احتمال تعذر الوصول إلى نطاق Vercel أو تعذر اتصال Vercel بالـupstream.
7. عامل Cloudflare الاحتياطي الموجود هو نسخة Preview داخل Cloudflare نفسه، وليس مزوداً مستقلاً؛ لا يحل انقطاع/حجب Cloudflare.
8. ملف `server.js` القديم proxy ثابت إلى Worker، ولا يمثل تطبيق API مستقلاً قابلاً للانتقال؛ لا يجوز اعتماده كحل بديل دون إعادة تصميم.
9. كود Worker يعتمد على واجهات Cloudflare مباشرة، أهمها D1 عبر `env.DB.prepare(...)` وWorkers AI عبر `env.AI`، إضافة إلى دورة `fetch/scheduled` وموارد التخزين S3-compatible عبر `aws4fetch`. لذا فإن نسخ Worker إلى Node.js/AWS كما هو لن يعمل؛ يلزم فصل طبقة التخزين/البيانات/الذكاء الاصطناعي والمهام المجدولة بعقود واضحة، ثم تنفيذ adapter واختبارات عقد مستقلة.
10. لا يوجد دليل حتى هذا التاريخ على أن DNS أو TLS أو API أو التخزين تم اختباره من شبكة يمنية دون VPN. لذلك لا يصح إعلان حل المشكلة.

## الفجوات البرمجية التي يجب إغلاقها قبل اعتبار المرحلة 8 مكتملة

### أ. طبقة تشغيل مستقلة عن Cloudflare
- استخراج واجهة runtime واضحة للبيانات، التخزين، الذكاء الاصطناعي، والمهام الخلفية.
- حصر استدعاءات D1 المباشرة ومخطط SQL المستخدم قبل اختيار بديل قاعدة البيانات.
- عدم تغيير قاعدة الإنتاج أو نقل البيانات في هذه الخطوة.
- بناء نسخة API مستقلة ببيانات اصطناعية وموارد اختبار منفصلة فقط.
- المحافظة على عقود REST الحالية، المصادقة، CORS، idempotency، Range، والرفع المجزأ.

### ب. إثبات مسار الاتصال
- التحقق من كل hostname عام يدخل في المسار الفعلي: نطاق التطبيق/API، DNS A/AAAA، TLS، REST، الوسائط.
- التأكد من أن التطبيق لا يحتوي fallback مضللاً يعيد الطلب إلى نفس المضيف باسم مختلف.
- اختبار endpoint احتياطي مستقل عن Cloudflare، لا Worker ثانٍ على Cloudflare.
- إعداد failover لا يكرر العمليات غير الآمنة ولا يسبب ازدواج الرسائل/الرفع.
- عدم اعتبار اختبار CI أو بلد آخر بديلاً عن اختبار اليمن.

### ج. سلامة الوسائط
- الاحتفاظ بالمرفقات وعدم حذفها تلقائياً بعد 72 ساعة وفق التغيير المعتمد.
- إبقاء سجل إعادة المحاولة عند فشل حذف كائن مؤقت فقط، وعدم حذف محادثات أو ذكريات أو ملفات المستخدم.
- المحافظة على اختبار الرفع المجزأ والتنزيل وRange وSHA-256 والصلاحيات الذي نجح على Preview.

## خطة التحقق المؤجلة للمرحلة 12

تُجرى اختبارات المستخدم الفعلية لاحقاً، مع حزمة اختبار جاهزة تشمل:

- اختبار الانتقال إلى API الاحتياطي ثم العودة إلى الأساسي دون تكرار الكتابات.
- توثيق زمن الاستجابة ونسبة النجاح والأخطاء دون تسجيل أسرار أو بيانات شخصية.
