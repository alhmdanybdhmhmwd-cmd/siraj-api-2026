## ما أضيف الآن

- `scripts/barq-runtime-portability-audit.mjs`: جرد آلي لمراجع bindings المباشرة في ملفات Worker الأساسية.
- أضيف أمر `npm run audit:runtime-portability`.
- أضيفت خطوة إلزامية في Backend CI؛ تفشل إذا ظهر binding جديد أو اختفى binding معروف دون مراجعة صريحة.
- هذا الفحص لا يدّعي أنه حوّل التطبيق إلى Node/AWS؛ هو حارس يمنع تضخم الاعتماديات غير المرئية أثناء بناء طبقة النقل.

## الترتيب الصحيح لبناء المحرك المستقل

1. استخراج عقود `Database`, `ObjectStorage`, `AIProvider`, `JobScheduler`, `PushProvider` دون تغيير سلوك Worker الحالي.
2. نقل منطق الخدمات إلى وحدات محايدة لا تستقبل `env` الخاص بـCloudflare.
3. بناء adapters لـCloudflare أولاً وربطها بالعقود، مع تشغيل اختبارات Worker الحالية دون تغيير.
4. بناء adapter مستقل لقاعدة البيانات والتخزين والذكاء الاصطناعي في بيئة اختبار ببيانات اصطناعية.
5. اختبار تطابق عقود REST والرسائل والمرفقات والصلاحيات وidempotency وRange.
6. إعداد مزود مستقل وفحص DNS/TLS/HTTP من اليمن دون VPN في مرحلة الاختبارات الحية المتفق عليها.

## حدود واحتياطات

### مراجعة واجهة عميل libSQL الرسمية

تمت مراجعة مرجع `@libsql/client` الرسمي بتاريخ 2026-11-22:

- توقيع `batch(stmts, mode?)` يقبل كائنات `{ sql, args }` ويضمن تنفيذ الدفعة كوحدة ذرية؛ وضع `write` صالح للدفعات التي قد تحتوي كتابة.
- `execute(stmt)` يقبل SQL string أو كائن statement مع args، لذا فتمرير `{ sql, args }` في prepared statements صحيح.
- `executeMultiple(sql)` مخصص لتسلسل أوامر SQL مفصولة بفواصل منقوطة، وهو المسار الصحيح لملفات migrations.

تم إصلاح موائم libSQL بحيث لا يعود إلى `execute({ sql })` عند غياب `executeMultiple`؛ ذلك المسار قد ينفذ أمراً منفرداً ولا يفي بعقد تشغيل ملفات SQL المتعددة. أصبح الموائم يفشل بوضوح عند غياب هذه القدرة، وأضيف اختبار يمنع التراجع إلى السلوك المضلل.

المراجع الرسمية: [Client API](https://tursodatabase.github.io/libsql-client-ts/interfaces/Client.html) و[Transaction modes](https://tursodatabase.github.io/libsql-client-ts/types/TransactionMode.html).

تم تجاوز اختبار طبقة قاعدة البيانات وحدها إلى تشغيل Worker نفسه من خلال `fetch()` مع حقن موائم libSQL المحلي:
