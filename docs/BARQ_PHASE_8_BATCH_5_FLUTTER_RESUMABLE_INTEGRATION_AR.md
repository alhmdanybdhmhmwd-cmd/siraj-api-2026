# المرحلة 8 — ربط Flutter بالرفع المجزأ

## ما تم تجهيزه
- إبقاء الملفات حتى 4 MiB على مسار الرفع الحالي دون تغيير.
- توجيه الملفات الأكبر من 4 MiB وحتى 60 MiB إلى جلسة رفع قابلة للاستئناف عبر Vercel proxy.
- إرسال كل قطعة بحجم أقصى 1 MiB إلى `/api/media/uploads/{sessionId}/chunks/{chunkNumber}`.
- إكمال الجلسة عبر `/complete` بعد تأكيد نجاح جميع القطع.
- إعادة محاولة محدودة (حتى ثلاث محاولات) للقطعة عند أخطاء النقل أو أخطاء الخادم، وعدم تكرار أخطاء العميل 4xx.
- حفظ مفتاح idempotency في التخزين الآمن باستخدام بصمة SHA-256 للملف وبيانات المحادثة؛ إذا أعاد المستخدم محاولة رفع الملف نفسه إلى المحادثة نفسها، يُعاد استخدام جلسة الرفع بدلاً من بدء جلسة جديدة.
- معالجة الجلسة التي اكتمل رفعها بالفعل، وحذف مفتاح الاستئناف الآمن بعد تأكيد الإكمال.
- تحديث `pubspec.yaml` و`pubspec.lock` لاستخدام مكتبة crypto الموجودة أصلاً في القفل.

## أثر الأداء المقصود
- الملفات الصغيرة لا تمر عبر مسار التقسيم.
- الملفات الكبيرة تستخدم طلبات متتابعة حالياً لتجنب سباق تجميع جزأين متزامنين في رقم multipart نفسه. هذا اختيار محافظ للسلامة، وليس تحسيناً نهائياً للسرعة.
- لم تُقَس السرعة بعد؛ نحتاج قياس زمن رفع ملفات بأحجام متعددة ومقارنته بالمسار السابق بعد إذن الاختبار. يمكن دراسة توازٍ محدود لاحقاً إذا أثبتت الاختبارات سلامة التزامن.

## الملفات
- `android/lib/main.dart`
- `android/pubspec.yaml`
- `android/pubspec.lock`
- `docs/BARQ_12_PHASE_MASTER_PLAN_AR.md`

## ما لم يحدث
- لم يتم تشغيل اختبارات أو `flutter pub get` أو CI.
- لم يتم نشر Preview أو Production.
- لم يتم تغيير DNS أو إعدادات Vercel/Worker/Tigris الإنتاجية.
- لم يُجر اختبار حي من اليمن دون VPN؛ لا يوجد إعلان بحل المشكلة.

## المطلوب بعد إذن المستخدم
1. مراجعة وتحليل static لمسارات بدء الجلسة والرفع والاستئناف والإكمال والإلغاء.
2. اختبارات وحدات لتقسيم القطع وحدودها وبصمة الاستئناف.
3. اختبارات تكامل محلية/CI للخادم والـProxy وD1 migrations، بما فيها فشل الشبكة وإعادة المحاولة والتنظيف.
4. اختبارات Flutter وتحليل static وتوافق dependency lock.
5. قياس أداء 4–5 MiB و10 MiB و30 MiB و60 MiB، دون نشر حي.
6. عرض النتائج للمستخدم قبل طلب إذن منفصل لأي Preview أو اختبار حي.
